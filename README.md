# pinn-sirius: GitHub → Kaggle

Код хранится в GitHub. Каждый отправленный в GitHub коммит автоматически проверяется в приватном
офлайн CPU-запуске Kaggle через GitHub Actions. GPU-обучение запускается отдельно.
Фоновые GPU-сессии не используются.
По умолчанию: приватный Kaggle script, CPU, без установки дополнительных пакетов.

## Подготовка управляющего окружения (однократно)

```bash
python -m venv .venv
.venv/bin/pip install kaggle six
```

`KAGGLE_API_TOKEN` должен быть задан через секреты окружения, не через файлы репозитория.
В текущем облачном окружении CLI уже установлен в `/workspace/scratch/kaggle-venv`.
Репозиторий сейчас публичный; управляющее окружение скачивает код без GitHub-токена.
Если сделать его приватным, сначала потребуется добавить авторизацию скачивания в управляющем окружении.
Данные и веса в публичный репозиторий не загружать.

## Проверка всей цепочки без GPU

Сначала commit и push, затем:

```bash
python scripts/kaggle_run.py --wait
```

Скрипт проверяет чистоту рабочего дерева и наличие коммита в GitHub **до**
выделения ресурсов Kaggle. Управляющее окружение скачивает ZIP выбранного SHA из GitHub и передаёт код
в Kaggle вместе с запуском. Kaggle работает офлайн,
выполняет `kaggle/smoke_test.py`: 100 шагов обучения коэффициента y = w*x
стандартным Python без сторонних библиотек. Ожидаемый вес: 2, loss < 1e-10.
Результат, checkpoint и манифест скачиваются в `.kaggle-runs/<run>/output`.
Kaggle URL и параметры находятся в `.kaggle-runs/<run>/submission.json`.

## Когда появится настоящий код

Положить свой скрипт, например, в `train.py`. Читать:

- `INPUT_DIR` — `/kaggle/input`: подключённые датасеты, веса, прошлые результаты;
- `OUTPUT_DIR` — `/kaggle/working`: сохраняемые результаты и checkpoints;
- `RUN_COMMIT` — SHA кода, на котором запущен эксперимент.

Проверить короткий прогон на CPU (аргументы `--max-steps` должны поддерживаться вашим кодом):

```bash
python scripts/kaggle_run.py --entrypoint train.py --dataset OWNER/DATASET --wait -- --max-steps 2
```

После успешной проверки запустить GPU явно:

```bash
python scripts/kaggle_run.py --entrypoint train.py --gpu --dataset OWNER/DATASET --max-training-minutes 120 --wait --timeout-minutes 150 -- --max-steps 1000
```

Все аргументы после `--` передаются train.py без изменений.
Пока вашего train.py нет, проверен только пример; адаптация его зависимостей,
чтения данных, аргументов, CUDA и checkpoint/resume потребуется после загрузки.

## Как экономить квоту

1. Использовать встроенные библиотеки Kaggle. По умолчанию pip не запускается.
   Не переустанавливать torch/CUDA без конкретной необходимости.
2. Только недостающие зависимости указывать в отдельном requirements файле:
   `--requirements requirements-kaggle.txt --internet` (если интернет Kaggle доступен). Используются обычные правила pip:
   удовлетворённые зависимости не переустанавливаются, `--upgrade` не применяется.
3. Для пакетов без доступа к PyPI заранее подготовить совместимые с Kaggle wheels
   в Dataset и указать `--wheelhouse /kaggle/input/DATASET/wheels` вместе с
   `--requirements ...`. Будет использован `pip --no-index`.
   Это сокращает загрузки, но установка в свежую сессию всё равно нужна.
4. Большие данные и базовые веса хранить в Kaggle Dataset и подключать `--dataset`;
   не скачивать их из Hugging Face/GitHub заново в каждом GPU-запуске.
5. Ограничивать шаги/эпохи, применять early stopping в своём коде.
   Наш launcher ограничивает время процесса обучения: по умолчанию 60 минут,
   переопределяется через `--max-training-minutes`. Это аварийное завершение,
   поэтому сохранять checkpoints надо регулярно, а не только в конце.
6. Для продолжения подключить `--checkpoint-kernel OWNER/PREVIOUS-KERNEL`.
   Его output появится под `/kaggle/input`; путь передать вашему train.py через
   поддерживаемый им `--resume`. Сам launcher не реализует resume за модель:
   train.py должен сохранять и восстанавливать модель, optimizer, scheduler,
   шаг, при необходимости scaler и RNG.
7. После завершения скачать и проверить checkpoints. Локальные файлы
   `.kaggle-runs` не коммитятся; долгосрочные веса хранить отдельно.

Каждая сессия Kaggle свежая. Постоянный кэш зависимостей между запусками не
гарантируется. Интернет в kernel по умолчанию выключен: код уже передан в запуск.
ZIP кода ограничен 750 KB, чтобы случайно не отправить данные/веса через Kernel API.
Для установки пакетов предпочитать подготовленные wheels в Dataset.
Флаг `--internet` доступен явно, но доступность сети зависит от аккаунта Kaggle.
GPU-сессия тратит время также на подготовку; её длительность отражается в
`run-manifest.json` (`setup_seconds`, `elapsed_seconds`). Подключение Dataset
сокращает внешние загрузки, но не гарантирует нулевое время подготовки.
Конкретный набор пакетов и ускоритель оптимизируем после появления кода и модели.

## Контроль запуска

```bash
kaggle kernels status OWNER/KERNEL
kaggle kernels output OWNER/KERNEL -p ./results
```

`--wait` ждёт до 30 минут по умолчанию. Его timeout **не останавливает** удалённый
запуск: перед повторным запуском проверить статус в Kaggle. При необходимости
остановить через страницу kernel. Дополнительно в Kaggle API передаётся лимит сессии: время обучения + 10 минут
на подготовку. Его соблюдение зависит от платформы; таймер subprocess ограничивает
сам процесс обучения. При timeout возможен незавершённый последний checkpoint.
При ошибке launcher сохраняет манифест с причиной; Kaggle дополнительно хранит лог.
GPU-квота и доступность ускорителя зависят от аккаунта и правил Kaggle.


## Автоматическая проверка каждого коммита

Workflow: `.github/workflows/kaggle.yml`, вкладка GitHub **Actions → Kaggle CPU checks**.
Срабатывает при push в любую ветку; при пакетном push проверяет каждый SHA отдельно
(до 256 коммитов, сверх этого workflow явно завершается ошибкой). Локальный commit
без push не виден GitHub и ничего не запускает. Повторный push того же SHA в другую
ветку и ручной rerun могут повторить проверку.

Требуется repository secret `KAGGLE_API_TOKEN`: Settings → Secrets and variables
→ Actions → New repository secret. Не добавлять значение в код или workflow.
Без секрета workflow выдаёт понятную ошибку до обращения к Kaggle.

CPU-тест имеет лимит процесса 5 минут, запрос лимита сессии 15 минут. GPU и pip
в Kaggle выключены. Контроллер в GitHub устанавливает зависимости отдельно.
Внутри одного push коммиты проверяются последовательно, ошибки одного не отменяют
остальные. Разные push могут выполняться параллельно. Это расходует CPU-ресурсы
и лимиты Kaggle/GitHub Actions: автоматизация не означает отсутствие квот.
При отмене GitHub job уже отправленный Kaggle kernel может продолжать работу;
он ограничен заданным временем сессии. Статус и ссылка есть в GitHub job summary.
Выходные файлы остаются в приватном Kaggle kernel, в публичные Actions artifacts
не загружаются. Не печатать приватные данные в stdout: логи GitHub Actions публичны.

Пока автоматически выполняется `kaggle/smoke_test.py`. После загрузки настоящего
кода адаптировать этот smoke test к короткой проверке модели на CPU, без полного
дообучения. Для коммитов до появления инфраструктуры launcher отсутствует —
автоматическая проверка таких исторических коммитов завершится ошибкой.
